# Implementation contract v0.3

The user's current instructions supersede the attached v0.1 draft where it defers MCP: **the MVP is web UI → agent HTTP API/MCP client → separate MCP record server**. Only the MCP record server reads patient files. The original clinical scope remains: synthetic outpatient diabetes pre-visit profiles, source-linked facts, explicit uncertainty, no diagnoses, prescribing, orders, or source-record writes. The coding agents below build one runtime agent, not multiple clinical agents.

## Fixed choices and ownership

| Area | Decision | Owner |
|---|---|---|

| Agent service | Python 3.12, FastAPI/Pydantic, localhost:8000; one bounded coordinator | agent builder |

| Patient source | Versioned `records-mcp/data/patients/*.json`, read-only MCP mount `/records-mcp/data/patients` | record builder |
| Golden answers | `evaluation/cases/dev.jsonl` and `candidate_holdout.jsonl`; evaluator only | evaluator |
| Telemetry | OpenTelemetry in each backend; structured logs to stdout; local Collector plus local trace backend | telemetry builder |

Resolve exact patch dependencies from official releases once, commit Python and npm lockfiles and image digests, then reuse them. Record verified SDK/protocol compatibility in the root README. Do not silently downgrade if this protocol is unavailable; report a concrete compatibility issue. No dependency is installed or application implemented by this kit.

Containers are required for the MCP server isolation proof; web/API run locally. Supply Docker Compose with a Podman-compatible alternative. The container may listen on 0.0.0.0 internally but publish only `127.0.0.1:8001:8001`. Read-only root, non-root user, dropped capabilities, resource limits, temporary writable `/tmp`, and only the patient folder mounted read-only. Never mount the repository, `evaluation/`, secrets, or agent SQLite into the record server. A process-only MCP command remains available for debugging. Optional observability containers have loopback-only published ports.

## Data and authority

The record schema is a patient object with `schema_version`, `dataset_version`, `patient_id`, `records`. Each record has `record_id`, `record_type`, `recorded_at`, `event_date` (nullable), `version`, and `content`. Synthetic `content.facts` contains factual tuples `section,key,value,date,qualifier`; required nonempty `content.text` supplies untrusted source text for excerpts. Facts are structured clinical fixture data, not answer instructions. No patient file contains expected calls, scenario tags, scores, faults, or expected output.

Fix `as_of` per evaluation. Exclude future clinical events; if event date is absent use recorded_at only for filtering/selection. Preserve the clinical fact date as null and explain that the known recording date is not a collection/event date. If values conflict, retain both source-linked assertions; no unsupported reconciliation. No record is not equivalent to a negative clinical finding. Unknown allergy status is not 'no known allergies'.

Local demo authentication uses an opaque UI session resolved by the API into allowed patients. Never trust client-supplied role or patient permission headers. The API issues a short-lived, signed, patient-scoped development token addressed to a particular MCP server, using an established JWT library with explicit algorithm/issuer/audience/expiry checks. Each MCP request independently verifies it. This is a synthetic local auth fixture, not a claim of OAuth compliance. External/hosted authorization must implement the applicable MCP authorization profile. Never forward browser tokens or model-provider API keys to MCP servers. Signing keys live in ignored local secrets; the MCP server receives verification material only. Patient IDs are hidden from model tool arguments; the server derives scope from the verified token, not trace baggage, model text, or a shared global variable. Test interleaved requests for two patients.

## Tool contracts

Register tools explicitly and publish JSON input/output schemas. Unknown fields fail validation. All functions are read-only; annotations document behavior but are not access control.

| Qualified name in the agent | MCP tool name | Model-visible input | Result |
|---|---|---|---|
| `records__list_records` | `list_records` | `{record_types?: string[], before?: ISO-date}` | scoped record metadata (including `fact_keys`) and `inventory_complete` |
| `records__read_records` | `read_records` | `{record_ids: string[]}` | exact records, with versions and provenance |

Both return an envelope `{schema_version, status, patient_id, data, error, dataset_version}` with status `ok`, `empty`, `unavailable`, or `denied`. The client verifies the effective patient_id against its run context. Authentication failure before a patient is established returns an HTTP auth error, not an invented patient envelope. Errors have stable codes and retryability. Keep MCP protocol errors distinct from tool execution errors; normalize in the client adapter and honor isError/structured output conventions of the pinned SDK. Denied requests expose no records. Resolve opaque IDs against the authorized index; never concatenate IDs into paths. Maximum 20 IDs/read, 100 records/inventory, 100 KB/result; a larger inventory is incomplete, never silently truncated and called complete. Unsupported versions and malformed envelopes fail closed. `agent-service/config/record_tools.json` contains approved input/output JSON Schemas; `evaluation/schemas/` contains patient/profile schemas.

Inventory metadata adds `fact_keys`, the sorted unique `content.facts[].key` values, without values or note text. These keys support selection, not clinical evidence. Only a fully inspected zero-result inventory may return `empty` with `records=[]` and `inventory_complete=true`; `ok` requires at least one record. A truncated inventory is `ok` with `inventory_complete=false`; if no entry fits the size limit, return `unavailable/result_too_large` (not retryable).

Reads are atomic: `ok` contains exactly the unique requested IDs, with no omissions or extras. A missing or out-of-scope member makes the whole batch `denied/record_not_accessible` (not retryable), without revealing which ID exists. Any temporary member failure makes the whole batch `unavailable/record_unavailable` (retryable). Size overflow returns `unavailable/result_too_large` (not retryable). All failures have `data=null`; `read_records` never returns `empty`. The client verifies ID-set equality in addition to schema validation. Retry the identical failed batch at most once when retryable; do not split failed batches automatically or spend another retry allowance on the same failure.

MCP server registry lives in `agent-service/config/mcp_servers.json`. Each entry specifies stable ID, allowlisted URL, protocol revision, enabled flag, token audience, logical allowed tools, schemas/version fingerprints and timeouts. Discover definitions through MCP, intersect with the explicit allowlist, validate compatibility, then adapt to model function schemas. Do not auto-enable newly discovered tools. Resolve name collisions by server qualification; no arbitrary caller-supplied server URLs. Credentials and patient context are request-scoped even when connections are reused.

Adding a tool: typed handler + schema + explicit server registration + client allowlist entry + contract/evaluation fixtures. Adding a server: implement the same adapter interface, add a registry entry and server credentials, then run the unchanged control suite. Prove this with a test-only second server containing an innocuous `ping` tool and a same-server optional `get_record_counts` tool; neither enters the clinical allowlist by default. The coordinator and UI must not change for either proof.

## Agent and HTTP contract

Mandatory baseline: inventory once, then read all conditions, medications and allergies; the latest visit note; and the latest records for each relevant lab key (`HbA1c`, `glucose`) and each available vital key. Determine candidates from `record_type` and inventory `fact_keys`. For each key/category, select the maximum `event_date` (fallback `recorded_at` only when null); retain all records tied on that selection date to preserve contradictions. Order ties by `recorded_at` then `record_id` for stable batching, de-duplicate IDs, and batch at most 20 per read. A record covering multiple keys is read once. These IDs are the deterministic baseline set; subsequent unique IDs count toward the additional-read budget. These lab keys are synthetic fixture conventions, not a real-world clinical coding vocabulary. The application adds `before=as_of` to list calls and forbids the model from widening the date boundary. Additional reads are chosen by the model to inspect earlier results or conflicting history. Records actually read through MCP form the only allowed evidence context. Patient picker uses a minimal authorized ID/label catalog, not patient clinical files. The stub receives these same tool results and must not import evaluator case IDs, expected outputs or representative traces.

For reproducible local login, implement `POST /v1/demo/session` with a demo username/passphrase checked against ignored server-side `DEMO_SESSIONS_PATH` configuration. Return an opaque HTTP-only SameSite=Strict session cookie and expose `DELETE /v1/demo/session` for logout. These routes are enabled only in the synthetic local profile. Web fetch includes credentials, API permits only `http://127.0.0.1:5173`, and state-changing routes validate Origin/CSRF protection. No browser input may supply allowed patient IDs. Use 127.0.0.1 consistently in local URLs to avoid cookie host mismatches. This authentication fixture must not be enabled in hosted/real-patient operation.

Budget: six model calls, ten additional record IDs (baseline excluded), 60 seconds total wall time. Use five-second tool attempt timeout, one transient read retry with backoff; all attempts consume total deadline. Never retry denial, schema failure, or bad arguments. A budget exhaustion or retrieval outage yields an explicitly incomplete profile from verified facts, or failure if no usable evidence exists. Explicit empty inventory is a complete retrieval with missing-data gaps, not an outage. Cancellation/disconnection stops further scheduling; record interrupted runs on restart and do not silently resume costly model work.

Persist run start before calling models; fail closed if persistence unavailable. Use request ID + caller + canonical input hash for idempotency; same ID/same input reuses the run, different input returns conflict. SQLite is authoritative for run state/feedback, not telemetry. Do not hold database transactions across external calls. One API worker initially; concurrency limited to four active runs, overload returns 429. A tool-server outage reports degradation but saved profiles remain readable.

| Route | Behavior |
|---|---|
| GET /v1/patients | Authorized synthetic ID/label catalog |
| POST /v1/profiles | `{patient_id,visit_context,as_of,request_id}`; synchronous response with profile_id/run_id/trace_id, status, structured profile and source excerpts |
| GET /v1/profiles/{id} | Owner/patient-authorized saved output, sources and current review state |
| GET /v1/runs/{id} | Owner/patient-authorized run lifecycle, profile_id if available and safe error code |
| POST /v1/profiles/{id}/feedback | `{profile_version,review_revision,decision: accept|needs_correction,comment?}`; authenticated reviewer and version binding |
| GET /health/live and /health/ready | Liveness and dependency/degraded state; no sensitive content |

Profile payload: `{patient_id,status,facts:[],gaps:[],conflicts:[],sources:[]}`. Facts: `{section,key,value,date,qualifier,source_ids}`; sections condition/medication/allergy/lab/vital. Gaps: `{code,text}`. Conflicts: `{code,source_ids,text}`. Sources contain the read record IDs, versions, and excerpts. Runtime envelope adds IDs/usage, `profile_version` (integer, starts at 1), `review_status` (`draft|accepted|needs_correction`) and `review_revision` (integer, starts at 0). Retrieval `profile.status` and clinician review status are independent. Feedback checks both supplied versions atomically, appends an audit event, increments `review_revision`, and returns `{profile_id,profile_version,review_status,review_revision}`; stale versions return 409. Accept sets `accepted`; needs_correction sets `needs_correction`. New generated profiles start as draft; feedback does not edit clinical facts. GET and replayed profile responses include current review fields, so a reload cannot reset review state. Free text in gap/conflict descriptions may vary. Dates and numeric values must preserve source meaning. Service 403 for unauthorized patient (or consistent non-enumerating 404), 422 invalid input, 409 version/idempotency conflict, 502 invalid dependency output, 503 unavailable before evidence, and 200 with `status=incomplete` for usable partial evidence. Evaluation cases specify the canonical 403 branch.

Run lifecycle is `running|completed|failed|interrupted`, separate from profile completeness and review. Claim `(caller,request_id)` atomically before scheduling; duplicates never consume a second active slot or launch another model call. Identical POST replay: completed returns the saved profile with 200; failed returns its saved original error/status; running returns 202 with `{run_id,run_status:"running",profile_id:null}` and `Location: /v1/runs/{id}`; interrupted returns 409 with `code=run_interrupted` and the original run_id. GET run returns 200 with `{run_id,run_status,profile_id,error_code}`; use it to poll an already active run and follow profile_id when completed. On failure/interruption show the saved error. An explicit user restart must use a new request_id; reconnect/replay must not restart work. Scope checks apply before replay/polling, and changed inputs for a reused ID always return 409.

Code validates schema, source existence and patient scope, plus numeric/date consistency. An optional bounded model check does not establish clinical truth. Citations need semantic support assessed by evaluation and clinician review. Treat record text as data, never as system instructions. Safe rendering escapes record HTML/Markdown; no unsafe innerHTML or remote scripts. Output draft status persists until explicit feedback; accept records demo review only and never writes source records.

## Telemetry placement

Initialize telemetry from each backend's own observability directory at process startup. Use service names `clinician-agent-api` and `clinician-records-mcp`. Frontend logs only safe lifecycle failures and shows the returned run ID; browser tracing is optional. Propagate W3C traceparent across API→MCP, extracting/injecting per request without patient data in baggage. Do not send internal baggage to the model vendor. Use SDK-supported metadata hooks; test concurrency for trace isolation.

Spans: `profile.generate`, `model.call`, `mcp.call`, `records.list`, `records.read`, `profile.validate`, `profile.persist`. JSON logs contain timestamp, severity, service, environment, event, run_id, trace_id, span_id, tool/server names, status/error code, duration, retry count. Exclude patient IDs, clinical values, prompts, tool payloads, tokens, credentials, and complete URLs with queries. Emit aggregate latency/errors, token counts, tool attempts, timeouts and budget exhaustion metrics; avoid high-cardinality patient/run IDs as metric labels. Missing provider usage is unknown, not zero. Cost estimates require a versioned price table; otherwise report unavailable.

Collector configuration lives in `observability/otel-collector.yaml`; receive OTLP, apply memory limits/filtering/batching, then export to a local trace backend. Application logs go to stdout, captured per service under ignored `var/logs/` with rotation (10 MB × 3). Collector/trace storage under ignored `var/telemetry/`; default seven-day local retention. Instrumentation scrubs before export; collector filtering is defense in depth. Telemetry failure degrades observability with bounded queues; profile persistence must still work. Access/profile/feedback audit events live in SQLite separately, with actor, run, record reference, timestamp and action, without raw clinical payloads in operational logs.

## Evaluation and phases

Use actual JSONL fixtures supplied in `evaluation/cases/`. They include required read coverage, allowed batching, a representative call sequence, forbidden tools, expected structured output and prohibited assertions. Grade call coverage and dependencies, not a single ordering or batch shape. Clinical facts must reference successfully read records. Fault plans are evaluator-owned and injected through test-only harness setup, never a public tool argument.

12 development cases + eight candidate holdout cases, patient-disjoint. Candidate holdout is visible in this package and is not a blind clinical benchmark. Restrict runtime mounts and let an independent evaluator own it; create fresh clinician-reviewed cases for a stronger release claim. Compare fixed baseline with adaptive agent and run real-model cases multiple times. Stub runs prove plumbing only. The normalized observation schema rejects malformed traces, and the grader checks injected tool faults and matching retries. Actual fault injection, concurrency and model-budget enforcement still require runtime harness evidence. The included static grader is a starting point for structured fixtures, not a clinical validator; unsupported free-text medical claims require human review.

Stage A: lock contracts, fixture validation and dependency compatibility. Stage B: implement three real processes with offline model stub, MCP container, telemetry and browser tests. Stage C: configured real-model evals, extension proofs, then independent tester and human acceptance. Each stage records evidence; no next stage without explicit human acceptance. If delegation unavailable, one coding agent executes roles sequentially and labels independence as unavailable rather than inventing a second reviewer. Never report skipped model/clinician/runtime tests as passed.
